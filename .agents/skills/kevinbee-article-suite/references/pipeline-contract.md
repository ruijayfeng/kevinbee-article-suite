# 套件阶段契约

## 1. 发现

仅在用户需要近期方向时使用 `zhihu-ai-editorial`。交付来源与灵感，不代替作者选择。产品精确主题零命中时记录覆盖缺口，再定向核验第一方资料。

## 2. 写作

小红书任务按 [xiaohongshu-handoff.md](xiaohongshu-handoff.md) 走独立分支：原始材料或已有文章 → 小红书分析与分页文案 → 写作基础规则复核 → 同步文案与提示词 → 小红书图片 → 交付检查。小红书不经过下面的默认长文、正文配图与公众号排版步骤。

把 `Original Materials` 中的原始笔记、草稿、对话、截图说明和结果直接交给 `zh-writing-humanizer` 的默认公众号路线。`Cases` 与 `Voice Evidence` 可以补充事实索引，但不得替代原始材料。只有用户明确要求结构规划或稿件确有结构问题时，才读体验叙事诊断并制作 `story_map`。公众文章允许好奇、兴奋、吐槽和幽默；不编造经历，也不复制另一位作者的口癖。

若 `calibration/approved/` 中已有用户认可的同类文章，按 [feedback-loop.md](feedback-loop.md) 选最多两篇 `meta.json` 状态为 `approved` 且复盘完成的文章辅助校准。用户给出的当次材料和明确要求始终优先；样本不提供本篇事实，也不替代默认写作路线。

写作阶段通过条件：标题承诺由正文兑现；事实与原始材料相符；读者能跟上作者的动作和判断；段落提供新信息或必要停顿。篇幅由内容决定，不把“变短”当成去 AI 味指标。写完再按写作 Skill 的基础去 AI 规则审稿。

## 3. 图片

先列出现有素材的角色：input、process、result、failure、comparison、concept。证据图优先。只有文字存在难以理解的关系时，再让 `kevinbee-illustrations` 规划概念图；允许结论为无需生图。

## 4. 封面与文章配文

正文与标题定稿后再制作。封面使用 `cover` 模式，只表达一个核心对象和张力，并检查缩略图与平台裁切。文章配文从定稿正文提取最强结果或冲突，不重复标题，不许新增正文没有的测试、资料或承诺。

封面和配文可以按任务跳过；一旦生成，就必须回指正文中的真实内容。

## 5. 平台交付

公众号定稿 Markdown 交给 `gzh-design`，显式指定主题。保留原文、链接与图序，完成 HTML 校验和移动端预览。发布前还需实际处理图片上传与编辑器粘贴。知乎保留 Markdown，不生成公众号 HTML。小红书交付有序 PNG、发布标题与配文、文本审阅稿及生成与核验记录；只规划和样张可以独立交付，但不得记为整套发布准备完成。

## 6. 复核

技术检查与编辑检查分开：脚本检查缺失文件、占位和结构；人工检查叙事推进、作者声音、图片是否证明对应内容，以及封面和配文是否兑现正文。任何一项失败都返回负责该问题的上游环节，不由排版阶段改写正文。

用户改稿后，可将本轮草稿和修改稿交给回流流程。记录具体改动、用户明确反馈与适用范围；没有用户认可时只保留候选，不提升为以后写作的默认参考。不要根据一次改稿追加全局禁词或固定叙事模板。
